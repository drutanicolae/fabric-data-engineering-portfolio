## How to understand the DQ tables

Think of the five tables as different views of the same quality process:

1. **Rule catalogue (dim_dq_rule):** what is being checked and how to interpret it.
2. **Summary (dq_summary):** headline result for each rule. This is the best table for an overview screenshot and a Power BI summary page.
3. **Exception details (dq_exceptions):** which trip records triggered one or more rules, for investigation.
4. **Rule counts (dq_rule_counts):** a compact count by rule, useful for reconciliation and ensuring that rules with zero findings are still represented.
5. **Bridge (dq_exception_rule_bridge):** one row per exception-rule association, useful for analyzing exceptions by rule.

The distinction between exception rows and rule violations matters:
- dq_exceptions has one row per affected trip/exception record as currently designed.
- dq_exception_rule_bridge has one row per association between an exception and a rule, so its row count can exceed the exception table.
- Individual rule counts overlap. **Do not sum them to calculate unique affected trips.**
- The 6,023,630 exception rows and 7,443,414 associations are different measures and must not be presented as interchangeable totals.

| ZERO_DURATION | Pickup and drop-off timestamps produce zero duration | 915,742 |
| LONG_DURATION | Trip duration exceeds three hours | 28,528 |

The dq_summary screenshot shows all nine rules, issue counts, percentages, severity, interpretation and total row count of 78,423,712. Percentages use the total row count as denominator. Rule categories can overlap, so percentages must not be added to estimate the share of unique affected trips.

These rules are investigation signals, not automatic proof that a record is invalid. Negative financial values can have legitimate explanations such as refunds or adjustments, but the business meaning must be confirmed. Zero distance and zero duration may be valid edge cases or anomalies. The three-hour threshold is a project-defined review threshold, not an official TLC rule. Missing values should not be silently replaced with zero without a business decision.

## Semantic models and Power BI roadmap

Two semantic models exist:
- sm_nyc_taxi_gold for operational and financial analysis.
- sm_nyc_taxi_data_quality for quality monitoring.

The Data Quality model has dim_dq_rule added. Intended one-to-many, single-direction relationships run from dim_dq_rule[rule_id] to dq_summary[rule_id], dq_rule_counts[rule_id] and dq_exception_rule_bridge[rule_id]. These relationships still need final validation before the model is described as finalized. Do not connect the bridge to individual exception rows using source_file alone; it is not a unique trip key. A stable trip-level identifier is required for that relationship.

The Power BI reports have not been built yet. Planned reports:
1. **Data Quality:** rule counts and percentages, severity, source comparisons/trends where appropriate, and exception investigation.
2. **Operations & Finance:** trip volume, pickup/drop-off patterns, duration/distance, payment types, fares, tips and total amounts.

The intention is to publish both reports together in a Power BI App if the workspace configuration and licensing support it.
